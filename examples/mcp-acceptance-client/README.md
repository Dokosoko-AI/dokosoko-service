# Vendor-neutral Stateless MCPv2 acceptance client

This example is a standalone Go CLI for testing any HTTP endpoint that implements
Stateless MCPv2 revision `2026-07-28`. It is deliberately outside the DokoSoko
runtime and imports only the Go standard library.

Every run requires `server/discover`, `resources/list`, and `tools/list` to pass.
Additional checks become required when their corresponding flags are supplied:

- `resources/read` for each configured resource, or for the first advertised
  resource when one is available;
- an explicitly configured `tools/call`;
- expected tools and resource URIs;
- grant filtering with separate full-access and restricted bearer tokens;
- denial without explicit confirmation and, when deliberately enabled, the
  corresponding confirmed invocation;
- optional unauthenticated rejection.

The OAuth subcommands separately verify RFC 8414 metadata, RFC 7591 dynamic
client registration, authorization-code OAuth, RFC 8707 resource binding, and
PKCE S256.

Every MCP request carries a random JSON-RPC id and matching `X-Request-ID`, as
well as the `MCP-Protocol-Version`, `Mcp-Method`, and (for calls) `Mcp-Name`
headers required by the protocol revision.

HTTPS is the default transport boundary. Plain HTTP is accepted only for local
development, only for `localhost`, a `.localhost` name, or a loopback IP, and
only when the command explicitly names the endpoint's exact host and port with
`--allow-loopback-http`. The exception is not a global insecure-mode switch,
and redirects are never followed.

## Build and test

```sh
cd examples/mcp-acceptance-client
go test ./...
go build -o ./mcp-acceptance ./cmd/mcp-acceptance
```

## Public endpoint

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp/public \
  --allow-loopback-http localhost:8080 \
  --expect-tool search_knowledge \
  --format human
```

If a resource is advertised, the client reads the first one. Pin an exact
resource contract with a repeatable flag:

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp/public \
  --allow-loopback-http localhost:8080 \
  --expect-resource 'dokosoko://products/example/recipes/getting-started'
```

Localhost subdomains are supported with the same exact-authority opt-in:

```sh
./mcp-acceptance run \
  --endpoint http://api.vendor.localhost:33000/mcp/public \
  --allow-loopback-http api.vendor.localhost:33000
```

## Private endpoint with a bearer token

Use an environment variable or a mode-`0600` OAuth token file. There is no raw
token command-line flag, so credentials do not land in shell history.

```sh
export MCP_ACCESS_TOKEN='...'
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --expect-tool deployment.get_manifest \
  --call-tool deployment.get_manifest \
  --check-unauthenticated
```

For a token file generated by this CLI:

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --token-file ./mcp-token.json
```

Reports never contain request/response bodies, authorization headers, tool
arguments, or token values. JSON reports are suitable for CI:

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp/public \
  --allow-loopback-http localhost:8080 \
  --format json \
  --report-file acceptance-report.json
```

Exit status is `0` only when every executed check passed and every requested
check actually ran, `1` for an acceptance failure, and `2` for invalid
configuration or an operational error. Unconfigured optional checks remain
explicit `SKIP` evidence. A requested check whose prerequisite is missing is
`SKIP-REQUIRED`, increments `summary.required_skipped`, and makes the command
exit `1`; it can never produce a successful acceptance result.

## OAuth DCR and PKCE

The login command binds a temporary loopback listener before it prints the
authorization URL. It does not open a browser. Open the URL yourself; after
approval, the browser returns to the exact callback path and receives a small
success or error page with no OAuth values in it:

```sh
./mcp-acceptance oauth login \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --listen localhost:0 \
  --callback-path /callback \
  --state-file ./.mcp-oauth-state.json \
  --token-file ./mcp-token.json \
  --timeout 5m
```

Only `localhost`, `127.0.0.1`, and `::1` listener addresses are accepted, and
the actual bound address is verified as loopback. Port `0` selects a free port.
The literal `localhost` is preserved in the registered redirect URI when it is
used in `--listen`, which is useful for browser policies that distinguish it
from numeric loopback addresses.

The command discovers authorization-server metadata, validates PKCE S256
support, performs RFC 7591 DCR unless `--client-id` is supplied, waits at most
the configured timeout, and writes the bearer token to a new mode-`0600` file
without printing it. The state file remains available for manual recovery if
the callback times out.

OAuth metadata, authorization, registration, resource, and token endpoints use
the same HTTPS boundary. If a local authorization server uses another loopback
port, repeat `--allow-loopback-http` with that exact authority. The split flow
persists only those exact exceptions in its private resume file, so `oauth
finish` cannot widen them.

For environments where a callback listener cannot be used, the existing split
start/finish flow remains available. The start command writes a short-lived
resume file with mode `0600`:

```sh
./mcp-acceptance oauth start \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --redirect-uri http://127.0.0.1:7777/callback \
  --state-file ./.mcp-oauth-state.json \
  --token-file ./mcp-token.json
```

Open the printed authorization URL, copy the full loopback callback URL from
the browser even if no page is listening, and run the printed resume command:

```sh
./mcp-acceptance oauth finish \
  --state-file ./.mcp-oauth-state.json \
  --callback-url 'http://127.0.0.1:7777/callback?code=...&state=...' \
  --token-file ./mcp-token.json
```

The finish command verifies state, exchanges the code with the saved PKCE
verifier, writes the bearer token to a new mode-`0600` file without printing it,
and removes the consumed state file. State expires after 20 minutes. Existing
state and token files are never overwritten.

For a non-default metadata location, pass `--metadata-url`. For a pre-registered
public client, pass `--client-id` to skip DCR.

## Grant checks

Provide two valid identities: a primary token with the required grant and a
restricted token without it.

```sh
export MCP_ACCESS_TOKEN='...full identity token...'
export MCP_RESTRICTED_ACCESS_TOKEN='...restricted identity token...'

./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --grant-tool sandbox.create
```

The safe default checks that the grant-gated tool is present for the primary
identity and absent from `tools/list` for the restricted identity. To additionally
attempt the restricted invocation, provide arguments and opt in explicitly:

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --grant-tool sandbox.create \
  --grant-args-file ./sandbox-create.json \
  --verify-restricted-call-denied
```

That opt-in can execute the operation if the server has an authorization bug;
use an isolated test environment and idempotent arguments.

## Confirmation checks

An unconfirmed call is always attempted when `--confirmation-tool` is set and
must return JSON-RPC error `-32003` with a server-issued one-time confirmation
challenge. A confirmed call can have side effects, so it requires a second
explicit flag. The client repeats the exact arguments and idempotency metadata
with that challenge, then proves the consumed challenge is rejected on replay:

```sh
./mcp-acceptance run \
  --endpoint http://localhost:8080/mcp \
  --allow-loopback-http localhost:8080 \
  --confirmation-tool support.submit_feedback \
  --confirmation-args-file ./feedback.json \
  --verify-confirmed-call
```

Argument files are capped at 1 MiB and their contents are never included in the
report.
